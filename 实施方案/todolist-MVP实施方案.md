
> **以ESP32-S3智能音响为交互终端、以电脑为本地服务器的学生学习计划执行与监督系统。**

Todolist只是后端的一项基础能力。真正的产品核心是：

> **计划调度、语音交互、学习计时、主动提醒、状态管理和数据统计。**

这个定位与普通待办软件已经完全不同。

---

# 一、整体工程架构

建议将P1拆成三个部分：

```text
┌─────────────────────────────┐
│        电脑端后端系统         │
│                             │
│  学习计划 │ 调度引擎 │ 计时器 │
│  统计分析 │ 语音模板 │ 设备管理│
│  数据库   │ Web管理界面       │
└──────────────┬──────────────┘
               │ Wi-Fi局域网
               │ WebSocket / HTTP
┌──────────────▼──────────────┐
│        ESP32-S3语音终端       │
│                             │
│ 麦克风 │ 唤醒词 │ 音频采集    │
│ 扬声器 │ 提示音 │ 状态灯       │
└─────────────────────────────┘
```

各部分职责应明确区分：

## ESP32-S3负责

- 持续监听唤醒词
    
- 唤醒后采集用户语音
    
- 将音频发送给电脑
    
- 接收电脑返回的播报音频
    
- 播放定时提醒
    
- 显示连接、监听、学习等状态
    
- 网络中断时执行少量本地兜底功能
    

## 电脑后端负责

- 保存学习计划
    
- 判断当前应该执行哪个任务
    
- 维护学习开始、暂停、结束状态
    
- 计算实际学习时长
    
- 执行定时调度
    
- 语音识别
    
- 用户意图识别
    
- 生成播报内容
    
- 文字转语音
    
- 保存统计数据
    
- 提供计划管理界面
    

这种分工是正确的，因为ESP32-S3适合做持续监听、唤醒、采音、播放和简单命令处理，不适合承担完整的计划管理、复杂自然语言理解及长期数据分析。

ESP-SR官方能力本身已经包含音频前端、WakeNet唤醒词、MultiNet命令词识别和中文语音合成等模块；其中ESP32-S3上的MultiNet支持自定义中英文命令，最多可配置约200条命令。([Espressif Systems](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/getting_started/readme.html?utm_source=chatgpt.com "Getting Started - ESP32-S3 - — ESP-SR latest ..."))

# 二、语音交互应当分成两种工作模式

这是架构中的关键点。

## 模式一：离线固定命令

例如：

- “开始学习”
    
- “完成学习”
    
- “暂停学习”
    
- “继续学习”
    
- “休息一下”
    
- “今天有什么计划”
    
- “下一个任务是什么”
    

这类命令结构固定，可以直接在ESP32-S3本地识别。

流程是：

```text
用户说唤醒词
→ ESP32-S3本地唤醒
→ ESP32-S3识别固定命令
→ 向电脑发送结构化命令
→ 后端执行
```

发送的不是整段语音，而是类似：

```json
{
  "device_id": "speaker_001",
  "command": "START_STUDY",
  "timestamp": "2026-06-24T19:00:05+08:00"
}
```

这种方式的优点是：

- 响应快
    
- 不依赖大模型
    
- 不需要上传大量音频
    
- 即使语音识别服务暂时不可用，核心操作仍然可以执行
    

ESP32-S3上的WakeNet能够本地持续执行唤醒检测；官方文档显示其支持多个唤醒词模型，也提供定制唤醒词的流程。([Espressif Systems](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/wake_word_engine/ESP_Wake_Words_Customization.html?utm_source=chatgpt.com "Espressif Speech Wake-up Solution Customization Process"))

---

## 模式二：自然语言对话

例如：

- “今天数学计划往后推半个小时。”
    
- “我作业还没写完，再给我延长二十分钟。”
    
- “明天晚上七点提醒我背英语。”
    
- “我今天学了多久？”
    
- “取消今晚的物理复习。”
    
- “数学完成了，但是英语今天不想学了。”
    

这类内容无法只靠固定命令词完整处理，适合发送到电脑端：

```text
唤醒
→ ESP32-S3录制用户语音
→ 上传电脑
→ 电脑端语音转文字
→ 意图解析
→ 调用计划系统
→ 生成回复文字
→ TTS生成音频
→ ESP32-S3播放回复
```

所以产品不应该在“ESP32本地识别”和“服务器语音识别”之间二选一，而应该使用：

> **本地固定命令＋后端自然语言理解的混合方案。**

第一版可以先只实现固定命令，第二阶段再加入自然语言对话。

# 三、唤醒机制怎么设计

用户提出“说`XX，XX`唤醒”，这是可行的，但需要区分两个概念。

## 1. 唤醒词

例如：

- “小智小智”
    
- “小星小星”
    
- “同学同学”
    
- “学习助手”
    

唤醒词必须具备：

- 发音相对清晰
    
- 不容易在日常对话中误触发
    
- 音节不能太短
    
- 与常用词有明显区别
    
- 儿童发音也容易识别
    

不建议使用两个很短的单字，例如“喂喂”“来来”，误唤醒概率会很高。

ESP32-S3可以使用WakeNet在本地持续监听，不需要电脑持续接收房间里的全部音频。官方也提供唤醒词定制机制，但专属唤醒词是否需要额外训练、定制流程或费用，需要在正式产品化阶段进一步确认。([GitHub](https://github.com/espressif/esp-sr?utm_source=chatgpt.com "espressif/esp-sr: Speech recognition"))

## 2. 唤醒后的识别窗口

例如：

```text
用户：“小星小星”
音响：“我在。”
用户：“开始学习。”
```

也可以做成连续一句：

```text
“小星小星，开始学习。”
```

第一版建议先采用两段式：

```text
唤醒词
→ 提示音或灯光反馈
→ 3～5秒命令识别窗口
→ 执行命令
```

这样调试更简单，也容易判断失败发生在唤醒阶段还是命令识别阶段。

# 四、真正的核心不是语音，而是学习状态机

语音只是入口。

系统必须首先定义当前学习处于什么状态，否则“开始学习了”“完成学习了”会产生很多歧义。

建议至少定义以下状态：

```text
IDLE             空闲
WAITING_START    等待计划开始
REMINDING        正在提醒
STUDYING         学习中
PAUSED           已暂停
BREAK            休息中
OVERRUN          学习超时
COMPLETED        已完成
SKIPPED          已跳过
```

状态流转示例：

```text
WAITING_START
    ↓ 到达计划时间
REMINDING
    ↓ 用户说“开始学习”
STUDYING
    ↓ 用户说“暂停学习”
PAUSED
    ↓ 用户说“继续学习”
STUDYING
    ↓ 用户说“完成学习”
COMPLETED
    ↓
BREAK
```

定时到点但学生没有回应时：

```text
WAITING_START
    ↓ 到点提醒
REMINDING
    ↓ 5分钟无回应
再次提醒
    ↓ 仍无回应
记录为延迟开始
```

后端必须是状态的唯一权威来源。

ESP32-S3不能自己决定“现在已经学习了35分钟”，它只负责把“开始”“结束”等命令传给后端，并显示后端返回的状态。

---

# 五、“开始学习了”到底开始哪个任务

这是第一版必须解决的歧义。

假设当前有三个任务：

```text
19:00 数学作业
19:45 休息
20:00 英语背诵
```

学生19:07说：

> “开始学习了。”

系统应该按照以下规则查找任务：

1. 有没有正在等待开始的任务；
    
2. 有没有当前时间附近的计划任务；
    
3. 有没有已经提醒但尚未开始的任务；
    
4. 如果只有一个，直接开始；
    
5. 如果有多个，再语音询问确认。
    

例如：

```text
系统：
“现在应该开始数学作业，计划学习40分钟。是否开始？”

学生：
“开始。”

系统：
“数学作业已经开始计时。”
```

第一版可以进一步简化：

> “开始学习”默认启动距离当前时间最近、尚未完成的学习任务。

但这条规则必须明确写入需求，不能让开发人员临时判断。

# 六、定时语音播报的正确结构

用户提出的播报逻辑是对的，但应该拆成不同事件模板。

## 1. 提前提醒

例如提前5分钟：

```text
“张明同学，五分钟后开始数学作业，计划学习四十分钟，请做好准备。”
```

## 2. 到点开始提醒

```text
“根据六月二十四日学习计划，张明同学现在应该开始数学作业，计划学习四十分钟。”
```

## 3. 用户确认开始

```text
“数学作业已经开始计时，计划在十九点四十分结束。”
```

## 4. 计划时间结束

不能直接说“学习计划已经完成”。

因为时间到了，不代表学生真的完成了任务。

更准确的播报是：

```text
“数学作业计划时间已经结束。是否完成学习？”
```

学生回答：

- “完成了”
    
- “还没有”
    
- “再学十分钟”
    

然后系统再决定下一步。

## 5. 确认完成后

```text
“数学作业已完成，本次有效学习三十八分钟。现在休息十分钟，十九点五十分开始英语单词。”
```

## 6. 休息结束

```text
“休息时间结束。接下来是英语单词，计划学习三十分钟。”
```

这里需要修正一个关键产品逻辑：

> **计划结束时间到达，只代表预计时间结束，不等于任务完成。**

必须由学生确认完成，或者由系统记录为“到时未确认”。

---

# 七、播报内容自定义应该怎么做

不要让用户直接修改大量程序逻辑，而应当采用模板系统。

例如：

```text
模板名称：学习开始提醒

模板内容：
“根据{date}学习计划，{student_name}同学现在应该开始{task_name}，计划学习{planned_minutes}分钟。”
```

可用变量包括：

```text
{student_name}
{date}
{current_time}
{task_name}
{subject_name}
{planned_minutes}
{actual_minutes}
{break_minutes}
{next_task_name}
{next_start_time}
```

系统设置中允许：

- 启用或关闭某一类播报
    
- 修改播报文字
    
- 选择提前几分钟提醒
    
- 设置重复提醒间隔
    
- 设置最大提醒次数
    
- 选择音色
    
- 调整语速和音量
    
- 设置安静时段
    

但第一版不需要允许无限复杂的条件逻辑，只做变量替换即可。

# 八、电脑后端不能只是一个Web页面

电脑端需要包含至少六个核心服务。

```text
P1电脑端后端
│
├── 1. 计划服务
│   ├── 创建计划
│   ├── 修改计划
│   ├── 查询当前任务
│   └── 生成每日时间表
│
├── 2. 调度服务
│   ├── 提前提醒
│   ├── 到点提醒
│   ├── 结束提醒
│   └── 休息结束提醒
│
├── 3. 学习会话服务
│   ├── 开始
│   ├── 暂停
│   ├── 继续
│   ├── 完成
│   └── 计算有效时长
│
├── 4. 语音服务
│   ├── ASR语音识别
│   ├── 意图识别
│   ├── TTS语音合成
│   └── 播报模板
│
├── 5. 设备服务
│   ├── ESP32注册
│   ├── 在线状态
│   ├── 音量设置
│   └── 固件版本
│
└── 6. 统计服务
    ├── 学习时长
    ├── 完成率
    ├── 延迟时间
    └── 科目占比
```

另外还需要一个简单的Web管理端，用来：

- 制定当天学习计划
    
- 查看设备是否在线
    
- 查看当前任务状态
    
- 手动开始和结束任务
    
- 查看学习记录
    
- 修改播报模板
    
- 修正错误记录
    

语音不能成为唯一控制渠道，否则一旦识别错误，用户无法纠正数据。

# 九、ESP32-S3硬件端需要哪些能力

硬件端至少包括：

```text
ESP32-S3主控
数字麦克风或双麦克风阵列
音频功放
扬声器
按键
状态灯
USB供电
Wi-Fi连接
```

原型阶段建议有一个实体按键，至少支持：

- 短按：唤醒或确认
    
- 长按：停止播报
    
- 网络异常时重连
    
- 必要时恢复配置
    

状态灯可以表示：

|状态|灯光表现|
|---|---|
|空闲监听|常亮或低亮|
|已唤醒|呼吸或闪烁|
|正在录音|快闪|
|学习计时中|特定常亮状态|
|休息中|另一种状态|
|网络断开|红灯闪烁|

正式硬件可以自行组合ESP32-S3、I2S麦克风、功放和扬声器；但第一阶段为了减少音频硬件调试，使用带双麦克风阵列和完整音频链路的ESP32-S3语音开发板会更稳妥。乐鑫的ESP32-S3-Korvo-2就是面向语音识别和远近场唤醒的双麦克风开发板。([Espressif Systems](https://docs.espressif.com/projects/esp-adf/en/latest/design-guide/dev-boards/user-guide-esp32-s3-korvo-2-v3.0.html?utm_source=chatgpt.com "ESP32-S3-Korvo-2 V3.0"))

# 十、定时提醒不能依赖ESP32自己计时

建议以电脑后端的调度器为主：

```text
电脑后端到达提醒时间
→ 生成播报任务
→ 推送给指定ESP32设备
→ ESP32播放
→ ESP32返回播放结果
→ 后端记录提醒已执行
```

原因是：

- 学习计划保存在后端
    
- 用户可能临时修改时间
    
- 多个设备可能需要同步
    
- 电脑时间通常更可靠
    
- 所有提醒日志便于集中保存
    

ESP32可以缓存当天计划作为断网兜底，但不应该成为主要调度中心。

---

# 十一、必须处理电脑关机和网络中断

用户选择电脑作为后端，就意味着存在两个现实风险：

## 电脑关机

电脑关机后：

- 无法修改计划
    
- 无法执行后端语音识别
    
- 无法生成动态TTS
    
- 无法保存实时记录
    
- 定时提醒可能失效
    

## Wi-Fi中断

ESP32无法连接后端时：

- 命令无法同步
    
- 计时状态可能不一致
    
- 播报任务无法下发
    

因此原型阶段建议设置最低限度的离线兜底：

- ESP32每天同步当天计划
    
- 缓存当天的提醒时间
    
- 缓存常用固定播报音频
    
- 离线时仍能执行基本提醒
    
- 离线开始和结束记录先存在本地
    
- 恢复联网后补传记录
    

但这属于第二阶段。最初验证版可以明确要求：

> 电脑后端和局域网必须保持在线。

---

# 十二、第一版最合理的开发边界

第一版不要一开始就做完整自然语言助手。

建议按三个里程碑推进。

## P1-A：有声学习时钟

完成：

- 后端手动建立学习计划
    
- ESP32连接后端
    
- 到点自动语音播报
    
- 播放休息和下一任务提醒
    
- Web端手动开始、完成
    
- 后端记录实际时间
    

先验证：

> 电脑能否可靠控制ESP32按计划播报。

## P1-B：离线语音控制

增加：

- 本地唤醒词
    
- “开始学习”
    
- “完成学习”
    
- “暂停学习”
    
- “继续学习”
    
- “今天有什么计划”
    
- 后端状态同步
    

先只支持少数固定命令。

## P1-C：自然语言计划助手

再增加：

- 电脑端ASR
    
- 自然语言修改计划
    
- 延长学习时间
    
- 推迟或取消任务
    
- 查询统计
    
- 多轮确认
    
- 自定义语音回复
    

这样的顺序可以把问题逐层隔离。

---

# 十三、需要调整产品命名

从现在的定义看，“学习计划与提醒模块”已经不足以覆盖实际内容。

建议把P1定义为：

> **学习计划、执行与语音监督系统**

它至少包括四个核心域：

```text
P1
├── 学习计划
├── 学习执行
├── 语音交互
└── 学习行为统计
```

ESP32-S3不是一个附加外设，而是P1的主要交互终端；电脑端也不是简单后台，而是整个系统的控制中心。

最终架构可以概括为：

> **ESP32-S3负责听与说，电脑后端负责理解、调度、计时、记录和决策。**

当前最应该先确定的不是页面，而是三份核心设计：

1. 学习任务与学习会话的数据模型；
    
2. 学习状态机及语音命令对应关系；
    
3. 电脑后端与ESP32-S3之间的通信协议。
