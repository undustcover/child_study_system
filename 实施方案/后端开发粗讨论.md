可以先开发电脑后端，但这里要纠正一个概念：

> ESP32-S3不是“前端页面”，而是一个独立的设备端。  
> 电脑上的网页才是管理前端。

所以更准确的架构是：

```text
电脑后端
├── 业务逻辑
├── 数据库
├── 调度器
├── 语音与播报服务
└── 设备接口

电脑Web前端
├── 创建学习计划
├── 查看当前任务
├── 手动开始/暂停/结束
└── 查看统计

ESP32设备端
├── 唤醒
├── 语音命令
├── 麦克风采集
├── 扬声器播放
└── 与后端通信
```

# 可以先做什么

硬件到货前，完全可以先完成电脑端的大部分工作。

建议先实现以下内容：

## 1. 后端核心业务

先把这些逻辑写好：

- 创建、修改、删除学习计划
    
- 查询当天任务
    
- 判断当前应该执行哪个任务
    
- 开始学习
    
- 暂停学习
    
- 继续学习
    
- 完成学习
    
- 跳过任务
    
- 休息管理
    
- 有效学习时长统计
    
- 计划时长与实际时长对比
    
- 每日统计
    

这部分和硬件无关。

## 2. 学习状态机

必须先把状态流转做稳定：

```text
待开始
→ 学习中
→ 暂停
→ 学习中
→ 已完成
→ 休息中
→ 下一任务待开始
```

还要处理异常情况：

- 重复说“开始学习”
    
- 没有计划时开始学习
    
- 已经暂停时再次暂停
    
- 学习中直接启动另一个任务
    
- 计划结束但学生没有确认
    
- 休息超时
    
- 任务临时延长
    

## 3. 调度器

实现定时事件：

- 提前提醒
    
- 到点提醒
    
- 计划时间结束提醒
    
- 休息结束提醒
    
- 延迟未开始提醒
    

开始时可以让电脑直接播报，先代替ESP32。

## 4. 简单管理页面

先做一个最小Web页面：

- 添加任务
    
- 今日任务列表
    
- 开始、暂停、继续、完成按钮
    
- 当前任务计时
    
- 今日学习统计
    
- 播报模板设置
    

这样没有硬件，也能完整验证业务闭环。

# 不要只“留一个接口”

只说“给ESP32留接口”还不够。硬件到货前就应该先定义好设备通信协议。

至少要确定两类通信。

## ESP32发送给后端

例如：

```json
{
  "device_id": "box3-001",
  "event": "voice_command",
  "command": "START_STUDY",
  "timestamp": "2026-06-24T19:00:05+08:00"
}
```

其他命令：

```text
START_STUDY
PAUSE_STUDY
RESUME_STUDY
COMPLETE_STUDY
QUERY_CURRENT_TASK
QUERY_TODAY_PLAN
EXTEND_BREAK_5_MINUTES
```

## 后端发送给ESP32

例如：

```json
{
  "type": "speak",
  "message_id": "msg-1001",
  "text": "张明同学，现在应该开始数学作业，计划学习四十分钟。",
  "priority": "high"
}
```

还可能包括：

```text
播放语音
更新屏幕
调整音量
同步当前状态
同步当天计划
停止当前播报
```

# 推荐使用的通信方式

第一版建议：

- 普通管理接口：HTTP REST API
    
- 设备实时通信：WebSocket
    
- 数据格式：JSON
    

原因是：

- HTTP适合创建计划、查询统计
    
- WebSocket适合后端主动向ESP32推送提醒
    
- JSON便于调试和查看
    
- Python FastAPI同时支持这两种方式
    

第一版不必上MQTT。MQTT适合大量设备和物联网平台，但当前只有一台设备，先用WebSocket更简单。

# 硬件没到时怎么模拟ESP32

最好写一个“虚拟设备模拟器”。

它可以是一个Python小程序，模拟ESP32：

```text
连接后端
→ 上报设备在线
→ 接收播报消息
→ 在电脑上打印或朗读
→ 手动发送“开始学习”
→ 手动发送“完成学习”
```

例如在命令行输入：

```text
start
pause
resume
complete
```

模拟器转换成设备协议发送给后端。

这样硬件到货后，ESP32只需要按照相同协议接入，不用重新改业务逻辑。

# 最合理的开发顺序

## 第一阶段：纯电脑端闭环

先实现：

```text
Web页面创建计划
→ 后端定时调度
→ 电脑语音播报
→ 页面按钮开始学习
→ 后端计时
→ 页面按钮完成
→ 生成当天统计
```

## 第二阶段：虚拟ESP32接入

实现：

```text
后端推送提醒
→ 虚拟设备接收
→ 虚拟设备模拟语音命令
→ 后端更新状态
```

## 第三阶段：真实BOX-3接入

硬件到货后：

```text
烧录官方示例
→ 验证麦克风
→ 验证扬声器
→ 验证Wi-Fi
→ 实现WebSocket
→ 替换虚拟设备
```

## 第四阶段：本地语音唤醒和命令

最后接入：

- 唤醒词
    
- 固定命令识别
    
- 播报
    
- 屏幕状态显示
    

# 现在可以暂时不开发的部分

硬件未到前，可以不碰：

- ESP-IDF环境
    
- BOX-3板级驱动
    
- 麦克风采集
    
- 扬声器驱动
    
- WakeNet唤醒
    
- MultiNet命令识别
    
- 屏幕UI
    
- 固件烧录
    

但接口协议、状态机和设备模拟器必须先做。

# 结论

可以马上开始电脑端开发，而且这是正确顺序。

但不是：

> 先写后端，随便留个接口，以后再接硬件。

而应该是：

> 先把业务后端、Web管理端、设备通信协议和虚拟设备一起完成，等硬件到货后，只替换设备实现层。

这样硬件接入不会反过来重构整个系统。下一步应该正式编写《P1 MVP需求规格》，先锁定数据模型、页面、状态机、接口和验收标准。
